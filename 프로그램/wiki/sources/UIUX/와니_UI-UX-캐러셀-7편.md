# 와니 — UI/UX 인스타 캐러셀 7편 (49장)

- 프로덕트 디자이너 와니의 인스타 카드뉴스 7개 시리즈. 각 장 끝에 "저장해두세요"가 붙는 **요약형 실무 팁**이고, 실측 데이터·A/B 결과는 하나도 없다. 규칙의 방향은 [[Nielsen_10-사용성-휴리스틱|닐슨]]·[[김경환_디자인-독학하기-브런치북|김경환]]과 대부분 겹치므로, 단독 근거가 아니라 **실행 체크리스트**로 쓴다.
- 위치 표기는 캡처 파일의 시각 코드(`091225` 등) — raw의 `=== 091225 ===` 구분선과 같다.

## 시리즈 A — AI로 UI 만들 때 기준 (091225–091331)

- **AI에게 화면을 "만들게" 하지 말고 이미 정한 부품 중에서 "고르게" 하라** (091244·091331). 결과를 가르는 건 프롬프트 길이가 아니라 먼저 준 디자인 기준의 명확도라는 주장.
- 미리 정해 둘 6가지 (각 장 1개씩):
  - **색은 값이 아니라 역할로** — Primary·Background·Surface·Text·Border·Danger. `#5B6CFF`보다 "Primary"라는 의미를 줘야 브랜드색이 바뀌어도 AI가 따라온다 (091225).
  - **글자도 역할로** — Display·Title·Body·Label·Caption마다 크기·굵기·줄간격을 고정. 안 정하면 비슷한 제목이 24·22·20px로 흔들린다 (091237).
  - **반복 부품(버튼·입력칸·리스트)은 공통 컴포넌트로 먼저 정의** (091244).
  - **상태까지 정의** — 버튼 Default/Pressed/Disabled/Loading, 입력칸 Default/Focus/Filled/Error/Disabled (091257).
  - **간격 숫자는 스케일 안에서만** — 예: 4/8/12/16/24/32. 12·15·18·21px처럼 매번 새 값을 만들지 않게 (091304).
  - **모서리 둥글기·그림자도 단계로** — Radius 스케일(OCR 일부 깨짐, 0/4/6/8…/Full 형태), Shadow는 Small/Medium/Large (091311·091324).

## 시리즈 B — UX 법칙 5가지 (091343–091421, 091349는 표지 겹친 중복 캡처)

- **힉스**: 선택지는 대표만 먼저 보이고 나머지는 "더보기"로. 없애라는 게 아니라 지금 결정하기 쉽게 (091343).
- **피츠**: 중요한 버튼일수록 크게, 손 닿는 곳에. 예시는 상단의 작은 결제 버튼 → 하단의 큰 결제 버튼 (091356).
- **제이콥**: 사용자는 남의 앱에서 더 오래 산다 — 검색은 상단처럼 익숙한 자리에 (091402).
- **근접성**: 관련 항목은 붙이고 다른 그룹은 띄운다. 간격이 다 비슷하면 그룹 경계가 안 보인다 (091408).
- **폰 레스토프**: 강조는 많이 할수록이 아니라 주변과 다를 때 강해진다 — 추천 요금제 **하나만** 주인공으로 (091415).
- 마무리: "예쁜가?"는 두 번째 문제. 먼저 이 페이지에서 꼭 강조할 것과 사용자의 다음 행동이 바로 보이는지 확인 (091421).

## 시리즈 C — 실수 방지 UX 4가지 (091431–091501)

- **결과를 먼저 알려라** — 삭제 전에 "포함된 파일도 함께 삭제" 같은 결과를 보여 준다 (091437).
- **나가기 전에 저장 안 한 내용을 알려라** — 뒤로가기 시 바로 닫지 말고 계속 작성할 기회를 남긴다 (091443).
- **확인 버튼에도 행동을 적어라** — [취소][확인] 대신 [취소][프로젝트 삭제] (091449).
- **되돌릴 길을 남겨라** — 즉시 삭제보다 휴지통, 또는 스낵바 "되돌리기" (091455).
- **원문 내부 불일치**: 정리 카드(091501) 2번은 "위험한 행동은 분리"인데 본문 2번(091443)은 "저장 안 한 내용 알림"이다. 정리 카드가 본문에 없는 항목을 넣고 본문 항목을 뺀 것 — **본문 4개를 기준으로 읽고**, "위험한 행동 분리"는 별도 원칙(→ [[Figma_UI-디자인-원칙-7가지|Figma 근접성]]의 종료 버튼 분리 예와 같은 취지)으로 본다.

## 시리즈 D — 버튼 이름은 역할로 (091508–091544)

- **컴포넌트 이름에 색·화면 이름을 넣지 마라** — "Blue Button"은 브랜드색이 바뀌면 틀린 이름이 되고, "Login Button"은 회원가입 화면에서 쓰는 순간 맞지 않아 같은 버튼이 화면마다 복제된다 (091520).
- 이름은 `Button` 하나로 두고 차이는 **4속성**으로: Hierarchy(Primary/Secondary/Tertiary) · Tone(Brand/Neutral/Danger) · Size(S/M/L) · State(Default/Pressed/Hover/Disabled/Focused) (091526).
- "구매하기"·"로그인"은 컴포넌트 이름이 아니라 **라벨** (091532). 피그마 속성이 코드 props와 같은 구조로 이어져 개발자도 따로 만들지 않는다 (091538).

## 시리즈 E — HMW (091552–091626)

- 문제를 정의한 뒤 곧장 기능을 떠올리면 첫 답에 갇힌다 → **"어떻게 하면 우리가 ~할 수 있을까?"로 해결 방향을 넓힌다** (091558·091603).
- 공식: 어떻게 하면 [사용자]가 [상황]에서 [원하는 변화]를 이룰 수 있을까? — **질문에 기능 이름 금지** (091615).
- 예: 취준생이 강의 속 중요 내용을 다시 찾기 어렵다 → 저장·최근 본 구간·키워드 검색·노트-출처 연결을 함께 비교 (091620).
- 적은 뒤 3점검: 기능 이름이 들어갔나 / 여러 해결책이 나오나 / JTBD 목적과 이어지나. 답이 하나만 떠오르면 질문이 너무 좁다 (091626).

## 시리즈 F — JTBD (091635–091710)

- 행동("음식을 주문한다")만 보고 플로우를 그리면 메뉴 선택→결제 완료에서 끝난다. 사용자가 원한 건 **"집에 도착하자마자 저녁을 먹는 것"**일 수 있다 (091647).
- 공식: [어떤 상황]에서 [무엇을 해서] [원하는 결과]를 얻고 싶다 (091652).
- JTBD 기준으로 보면 도착 예정 시간 확인·시간 맞춰 주문·배달 현황 확인 같은 **빠진 단계가 보인다** (091704).
- 점검 질문: "이 흐름은 사용자가 원하는 결과까지 이어지는가?" (091710).

## 시리즈 G — 문제 정의문 (091725–091758)

- 문제 정의문 = 누가, 어떤 상황에서, 무엇 때문에 어려움을 겪는지 한 문장 (091730).
- "쇼핑 앱에 찜 기능이 필요하다"는 문제가 아니라 **이미 해결책을 정한 문장** — 정하는 순간 찜 버튼 위치·디자인만 고민하고 최근 본 상품·상품 비교 같은 대안을 놓친다 (091735·091740).
- 공식: [사용자]는 [상황]에서 [원인] 때문에 [어려움]을 겪는다 — 기능 이름은 빼고 "사용자가 멈칫하는 순간"만 (091746).
- 기능을 정한 뒤 다시 문제로 돌아가 "이 기능이 다시 찾는 시간을 줄이는가?" — 아니면 우선순위에서 뺀다 (091758).
