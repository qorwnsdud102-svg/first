# 모바일 가로 키오스크 웹앱 함정

## 한 줄 정의

일반 모바일 브라우저로 "박스에 거치하는 가로 전체화면 키오스크" 웹앱(QR 진입, 서버 없는 정적 SPA)을 만들 때 반복해서 부딪히는 OS·레이아웃·검증 제약 모음. (사례: 2026-05-31 용돈 ATM 웹앱 — React+Vite, Vercel 배포)

## 핵심 주장 / 속성

- **전체화면은 사용자 제스처 후에만 가능** — `element.requestFullscreen()`은 탭/클릭 같은 제스처 핸들러 안에서만 허용. 첫 화면(탭 전)은 절대 자동 전체화면 불가. **iOS Safari는 페이지 전체화면 API 자체를 막아둠** → iOS·첫화면은 **홈 화면 추가(PWA standalone)가 유일한 길**. 안드로이드(삼성인터넷/크롬)는 탭 한 번이면 주소창 숨김 됨. → 대응: 첫 터치에 fullscreen 시도 + UA 감지해 브라우저별 "홈 화면 추가" 안내 UI + `matchMedia('(display-mode: standalone)')`/`navigator.standalone`로 이미 전체화면이면 안내 숨김.

- **`orientation.lock` 방향 불일치 함정** — 세로용으로 짠 `screen.orientation.lock('portrait')`가 남아 있으면, 가로 제품으로 바꾼 뒤 시작 버튼 탭 → 풀스크린 진입 → **화면을 세로로 강제** → "가로로 돌려주세요" 회전가드가 역으로 뜬다. 방향 바꾸면 lock 값도 같이 바꿔야. iOS는 lock 미지원이라 `try/catch` + CSS 회전가드(`@media (orientation: portrait)`) fallback 필수.

- **세이프존 여백 ↔ 콘텐츠 높이 트레이드오프 (박스 구멍 대응)** — 박스 흰 테두리가 화면 가장자리를 가리므로 콘텐츠를 안쪽으로. 그런데 가로폰 높이는 ~390px뿐. **중앙정렬 콘텐츠의 상하 여백 = (뷰포트H − 콘텐츠H)/2 이라, `.screen` padding을 늘려도 여백은 안 변한다**(센터링이라 padding 무관). 여백을 늘리려면 콘텐츠(키패드)를 줄이는 수밖에 없고 = 키가 작아짐. "상하 150px 여백"은 키패드 최소 높이(누를 수 있는 키 4줄 ≈ 200px) 때문에 **물리적으로 불가**. 가로는 여유 있어 큰 여백 OK, 세로는 키패드가 한계. → 여백 요구는 항상 키 크기와 시소임을 먼저 알리고 트레이드오프로 합의.

- **flex squish 버그** — `flex: 0 0 auto`(shrink-to-fit) 부모 안에서 자식이 `width: 100%`면 너비가 **min-content로 붕괴**한다(키패드가 세로로 눌려 보임). → 고정 `width: 340px` 같은 명시 폭을 줘야 의도한 비율이 산다.

- **가로 키보드 가림 + focus 버블 함정** — 가로에서 시스템 키보드가 화면 ~60%를 덮어 입력칸이 안 보임. 대응: 입력 포커스 중엔 콘텐츠 상단정렬 + 타이틀 숨김(`position: fixed` body면 키보드가 오버레이라 상단정렬이 통함). **단, 포커스 감지(onFocus/onBlur)를 `<section>` 전체에 걸면 그 안의 버튼을 탭할 때 버튼이 포커스→typing상태→`display:none`되어 클릭이 무효화된다**(완료/취소 버튼이 안 눌림). → 포커스 감지는 **입력 묶음(form/.setup-form)에만** 걸 것. 이건 시뮬레이션(입력값·검증은 정상인데 제출 안 됨)으로만 잡힌 버그.

- **키보드 액션키로 자동 제출** — 입력칸들을 `<form onSubmit>`으로 감싸면 IME의 "이동/완료/Go" 키가 폼 submit을 트리거 → 마지막 칸에서 자동 제출. 비-마지막 칸은 `enterKeyHint="next"`로 다음 칸 이동.

- **iOS 오디오 자동재생 unlock 패턴** — iOS는 사용자 제스처 없이 `audio.play()` 차단. 제스처 핸들러 안에서 `play().then(pause)`로 한 번 "잠금 해제"해두면 나중에(예: 성공 화면 마운트) `play()`가 동작. 싱글톤 `<audio>`를 `document.body`에 append하면 iOS 재생 안정성↑. success↔리셋 빠른 전환 시 `play()` 프라미스가 `pause` 뒤에 늦게 풀려 소리가 남는 race는 `wantPlaying` 토큰으로 방어. **포맷은 `.mp4`(영상 트랙 가능)보다 `.mp3`/`.m4a`(오디오 only)가 iOS에서 확실** (Content-Type도 video/mp4 → audio/mpeg로 바뀜).

- **Vite `public/`만 서빙** — 브라우저가 받아야 하는 정적 파일(오디오 mp3, favicon, manifest.json)은 `public/`에 둬야 루트 경로(`/ost.mp3`)로 서빙된다. 프로젝트 루트에 두면 서빙 안 됨.

- **인쇄 QR = 영구 URL 문제** — 박스에 인쇄하는 QR은 영구라 URL이 바뀌면(호스팅 이전/프로젝트명 변경) 죽는다. 기능상 무료 서브도메인(`*.vercel.app`)으로 충분하지만, 대량 인쇄·판매면 소유 도메인이 안전장치. **인쇄 직전에 URL 한 번 확정**하면 됨(그 전엔 자유롭게 사용). QR은 오류복원 H로 생성(훼손·로고 대비).

- **검증 환경 함정** — (1) 작업장 유선망(192.168.45.x)과 와이파이(192.168.0.x)가 **다른 서브넷**이면 폰↔PC LAN 직접 접속 불가(방화벽 Public 프로필도 차단). 폰 확인은 **공개 배포 URL로**가 정답(LAN 삽질 금지). (2) 헤드리스 Playwright는 레이아웃·로직·이벤트 검증엔 강력하지만 **iOS 실제 오디오 자동재생/orientation.lock은 검증 불가** → 실기기 필수. (3) Vercel CLI는 **PC 이름이 한글이면 `vercel login`이 HTTP 헤더에 못 넣어 깨짐** → 대시보드 Git 연동으로 우회.

## 내 생각 / 미해결 질문

- 세이프존 px는 박스 사각 구멍 실측 전엔 추정일 뿐 → 실기기+박스로 최종 확정 필요(콘텐츠 축소 vs 여백).
- iOS 오디오 자동재생은 내가(LLM) 소리를 못 들어 끝까지 실기기 확인에 의존 → "검증 불가 항목"을 명시적으로 남기고 사용자에게 위임하는 습관이 중요.
- 자동 가드 아이디어: fullscreen/orientation/standalone 분기 로직은 디바이스 매트릭스(iOS Safari / iOS Chrome / 삼성인터넷 / 안드로 크롬 × 브라우저/홈화면)별 표로 회귀 점검할 가치 있음.
