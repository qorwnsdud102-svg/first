# 단일 진실 원천 (동작 = 표시)

## 한 줄 정의

동작을 결정하는 값과 화면에 표시하는 값이 서로 다른 소스를 읽으면 "버튼만 ON, 실제로는 안 됨" 모순이 반복된다 — 하나의 헬퍼/컬럼을 유일 소스로 두어 미싱크를 구조적으로 불가능하게 만든다.

## 핵심 주장 / 속성

- **증상 패턴**: UI 는 "ON/작동중" 인데 실제 로직은 skip. 표시 코드와 동작 코드가 같은 개념을 **각자 재계산**하기 때문. 한 쪽만 고친 PR 이 빈 구멍을 남긴다(재발 단골).
- **해법 — 단일 헬퍼**: 사례(2026-07-19 집중 모니터링) — 락인 재점검 주기를 실제 skip 판정(`run_cycle`)과 UI 배지(`compute_skip_status`)가 각각 계산하던 것을, `effective_lock_interval_hours(kw, ag)` **단일 헬퍼**가 양쪽의 유일한 소스가 되게 함 → 미싱크 구조적 불가능. 플래그도 DB 컬럼 하나(`focus_monitor`)가 유일 소스.
- **뷰 분산 문제**: 같은 상태를 리스트·카드·상세·행 배지 등 **여러 뷰가 각자** 판정하면 한 곳 고치고 다른 곳 누락(2026-07-08/09 자동입찰 배지 반복 갭). → `autobid_state(is_active, adgroup_status, campaign_status)` 같은 **공유 헬퍼**로 표시 계산을 통일. 렌더 시점 계산이라 DB 를 안 건드리고도 거짓말이 없다.
- **검증법**: "같은 개념을 계산·판정하는 곳이 2개 이상인가?" → 있으면 헬퍼로 수렴시킨다. `inspect.signature` 회귀 가드로 "같은 인자를 두 함수가 다 받는지" 검사한 사례도 있음.
- **왜 강력한가**: 정합을 사람의 규율(양쪽 다 고치기)이 아니라 **구조**(유일 소스)로 보장 → "버튼만 ON" 클래스의 버그가 원천 차단.

## 다른 엔티티와의 관계

- [[다경로-데이터-모순-디버깅]] — 이 원칙은 그 문제의 **근본 해법**. 모순 디버깅이 증상 진입점이면, 단일 진실 원천이 예방 설계.
- [[karpathy-guidelines]] — surgical change 와 짝: 소스를 하나로 모으면 변경 지점도 하나가 된다.
- [[측정-지표-함정]] — 지표 정의도 한 곳에 모아야 왜곡이 안 퍼진다.

## 내 생각 / 미해결 질문

- 새 상태 플래그·주기·임계값을 도입할 때 "이 값을 읽는 곳이 이미 있나?" 를 먼저 찾아 **기존 소스에 얹을지 신설할지** 결정하는 습관이 미싱크를 예방한다.
