# 카페24 간편결제 직결 아키텍처

## 한 줄 정의

카페24 자사몰에서 **커스텀 옵션 UI(옵션카드 1개/3개/6개…)를 쓰는 몰**이 네이버페이·카카오 톡체크아웃 같은 간편결제를 붙일 때의 정석 구조. 핵심은 **카페24 네이티브 결제 스택을 타지 않고, 내 UI의 값만 모아 직접 POST → 체크아웃 URL로 직행**한다는 것. (사례: 리페아·히토·미드디)

## 핵심 주장 / 속성

- **대원칙: 네이티브 결제 스택 금지, 단일 출처 직결.** 커스텀 옵션카드 몰엔 카페24 네이티브 옵션등록(`#totalProducts`의 `.option_box_id`)이 아예 없다. 공식 버튼(`#NaverChk_Button`+`setOptionBox` 등)을 억지로 쓰면 카페24 검증 스택(`PRODUCTSUBMIT`→`checkOptionRequired`→…)이 "옵션 0개"로 판정하거나, 흉내낸 행이 드로어 미러 목록에 새어나와 **선택목록 오염·네이티브 팝업 부활·TOTAL 합산 오염**을 부른다. → 결제 진입은 전부 내 UI 한 곳(`repeCollectOrder`)에서 값 수집 → `repeClearBasket` → B0000 직접 POST → 체크아웃 URL 직행(네이버 `/exec/front/order/navercheckout?sType=basket`, 카카오 `createKakaoOrderSheet`→pay.kakao.com, 미승인 시 장바구니 폴백). 공식 버튼은 `display:none !important`.
  - **일반 원칙**: 커스텀 UI와 플랫폼 네이티브 UI를 **반씩 섞지 말 것.** 한쪽을 정본으로 정하고 다른 쪽은 완전히 숨겨라 — 두 상태기계가 같은 DOM을 공유하면 부수효과가 샌다.

- **변종코드는 네이티브 select 값으로 폴백.** 옵션 선택했는데 "옵션(구성)을 선택해 주세요" 반려가 나오면, 변종코드(item_code)를 `data-variant`나 `#totalProducts` 행에서만 찾다 실패한 것(몰/상품에 따라 카페24가 그 XHR·행을 안 만든다). 폴백:
  ```js
  var v = card.getAttribute('data-variant') || (opts[idx] && opts[idx].value) || VBI[idx] || '';
  ```
  `opts` = `select[name=option1]`의 유효 옵션(`o.value && o.value!=='*' && !o.disabled`)이라 카드 `data-idx`와 1:1. 카드 클릭이 `select.value`를 항상 세팅하므로 이 값은 늘 존재 → 신뢰성 최고. 자체 바로구매(A0000)·장바구니(B0000) 공통.

- **간편결제는 비회원 전용 서비스.** N Pay·톡체크아웃 간편구매 버튼은 **로그인 회원이면 카페24가 결제 스크립트 자체를 미주입**(`createKakaoOrderSheet` undefined, 네이버는 "구매 불가" 얼럿 HTML을 서버가 직접 응답). → **회원 숨김 가드 필수**: `ec_mem_level` 쿠키(즉시) 또는 `.xans-layout-statelogon` 노출(load 백업) 중 하나라도 회원이면 `#rpQuickPay` display:none. 검증은 반드시 로그아웃/시크릿창.

- **버튼 렌더 ≠ 주문 수락 (별개 게이트).** 네이버페이 공식버튼 `#NaverChk_Button`은 카페24가 서버에서 HTML+스크립트를 주입 — 관리자 인증키4종·노출함·캐시삭제 다 해도 **상품연동 배치반영 전엔 빈 껍데기**(innerHTML 0). 단, **버튼 "그리기"는 공개 SDK+버튼인증키만으로 스킨이 직접 할 수 있다**(가입완료 전에도): `checkout.naver.com/customer/js/checkoutButton.js`→`innerCheckoutButton.js`→`nhn.CheckoutButton.apply({EMBED_ID, BUTTON_KEY, …})`. **함정**: 로더·CSS가 둘 다 `document.write`라 페이지 로드 후 동적 로드하면 무음 실패 → `innerCheckoutButton.js`를 직접 script 태그로 + CSS `img.pay.naver.net/static/css/button/button2.css`를 link로 직접 주입. **버튼이 그려져도 주문 수락은 네이버페이센터 가입완료(4단계) 후에야** 뚫린다 — 각각 별도로 A/B 판별.

- **공식 결제유닛은 285px 고정폭 통짜.** 네이버 `.npay_storebtn_bx`·카카오 `#checkoutContainer`는 안쪽 요소만 CSS로 숨기고 flex 반반 줄에 욱여넣으면 깨진다(라이브서 width:auto·display:contents 시 버튼이 2px 또는 폭발). → **반반 레이아웃은 커스텀 버튼으로 만들고, 공식 유닛에서는 필요한 요소만 "이사"한다.** 예: 카카오 찜 버튼(`.__checkout_btn_wish`)만 내 결제줄로 옮김 — SDK가 요소에 직접 클릭 바인딩(addEventListener)이라 **요소째 옮겨도 핸들러가 따라온다**(무동작이면 위임클릭이므로 박스째 이사로 폴백). 공식 유닛 전체는 CONFIG 가역 스위치(`npayOfficialUnit`)로 숨김.

- **커스텀 담기는 픽셀 신호를 수동 발사해야 한다.** 카페24 페이스북 채널 픽셀의 AddToCart만은 `EC$("body")`의 `EC_PRODUCT_ACTION_BASKET` 이벤트를 리스닝(네이티브 담기만 발생). 직접 POST로 담으면 이 신호가 안 울려 AddToCart가 영영 0건. → 담기 성공 직후 `EC$(document.body).trigger('EC_PRODUCT_ACTION_BASKET', {product_no, contents:[…], total_price, currency:'KRW'})` 수동 발사(EC$ 가드+try/catch면 픽셀 미연동 몰서 무해). 검증은 `fbq.getState().pixels[0].eventCount` 증가로 — /tr 요청은 네트워크에 안 잡힐 수 있어 **네트워크 무발견≠미발사**.
  - **일반 원칙**: 플랫폼의 분석/추적이 "네이티브 액션 이벤트"에 물려 있으면, 그 액션을 우회했을 때 **같은 이벤트를 수동으로 재발사**해줘야 계측이 유지된다.

- **소셜 로그인 버튼은 스킨에 이미 완비.** 카카오/네이버 "1초 회원가입"은 `login.html`의 `.login__sns > .wrap_sns_log`에 마크업이 이미 있다(안 보이는 건 관리자 미활성 → `{$display_X|display}`가 `displaynone` 출력). 대표가 관리자 앱연동만 켜면 됨. **색 함정**: 카페24 기본 3단계 선택자(`.xans-member-login .login__sns … a{background:#fff}`)가 스킨을 이겨 흰 버튼이 되므로 브랜드색에 `!important` 필수(카카오 #FEE500·네이버 #03c75a). **가입 유도 링크는 `/member/join.html`이 아니라 `/member/login.html`로** 보내야 소셜 1초 버튼이 손님에게 노출된다.

## "안 된다"일 때 진단 순서

1. **로그인 상태부터 실측**(`ec_mem_level` 쿠키) — 회원 상태로 테스트한 것 아닌가.
2. **작동하는 몰과 A/B** — 같은 `repeCollectOrder→POST→checkout fetch`를 두 몰에 발사해 응답 원문 비교(가장 빠른 판별).
3. **네이버페이센터 단계 확인**(가입신청→심사중→시스템연동→가입완료) — 가입완료 전엔 비회원도 서버 거부.
4. **기능 문제는 레퍼런스 grep이 첫 행동** — "미드디는 되는데 우리 몰만 안 되면" = 이식 누락 의심 → 두 `detail.html`의 해당 함수를 라이브 결과와 함께 대조.
