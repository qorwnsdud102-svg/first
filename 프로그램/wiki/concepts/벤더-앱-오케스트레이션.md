# 벤더 앱 오케스트레이션 (소스 없는 상용 프로그램 외부 조종)

## 한 줄 정의

수정할 수 없는 상용 프로그램을 **창 밖에서 버튼 누르고 파일 놓는 방식으로** 자동화할 때,
"프로그램이 지금 무슨 상태인가" 를 무엇으로 판단하느냐가 성패를 가른다 — 로그 문구가
아니라 **버튼 enabled 조합**이 정답이다.

## 핵심 주장 / 속성

- **왜 무수정인가** — 벤더 패치를 계속 받아야 하므로 exe/dll 을 한 바이트도 못 고친다.
  원본 폴더는 동결하고 복사본에서만 작업한다. 이 제약이 모든 설계를 결정한다.
  (WinForms 컨트롤 제어의 기술적 함정은 별건 — 유저 메모리 `winforms-vendor-app-automation`)

- **로그의 성공 문구 ≠ 작업 종료.** 사례 (2026-07-30 19:50): 댓글 프로그램 로그에
  `<계정> 로그인 성공` 이 찍힌 **같은 초에** `작업 시작` 을 눌렀다가
  `비활성 상태입니다` 로 세트가 통째로 실패. 프로그램은 그 뒤로도 로그인 작업을
  마무리하는 중이라 상태가 `실행중` — 1초 뒤에야 `로그인 작업이 완료` 가 찍혔다.
  → **다음 버튼을 누르기 전에 상태가 `대기` 로 돌아왔는지 확인**한다. 로그는 진행 상황을
  보여주는 것이고, 상태 머신(버튼 enabled 조합)이 유일한 게이트다.

- **완료 문구를 부분 문자열로 찾으면 0건으로 조용히 끝난다.**
  `로그인 작업이 완료 되었습니다` 와 `추출 작업이 완료 되었습니다` 가
  완료 지문 `작업이 완료 되었습니다` 를 **그대로 품는다.** 통째로 검사하면 회차가
  시작도 전에 "완료" 로 잡혀 결과 0건이 성공으로 보고된다.
  → **줄 단위로 보고 앞의 수식어를 걸러낸다.** 벤더는 `<무엇> 작업이 완료` 형태로
  문구를 확장하므로, 오늘 안 겹쳐도 패치 뒤에 겹칠 수 있다.

- **우연히 되던 것은 조건이 바뀌면 반드시 깨진다.** 같은 코드의 다른 실행 경로(통합 창
  체인)는 몇 시간 전 실전에서 성공했다. 이유는 로그인과 시작 사이에 게시글 추출(수십 초)과
  브라우저 정리 대기(최대 60초)가 끼어 있어 **그 시간이 우연히 방패**였던 것. 세트 기능에서
  추출을 끄자 방패가 사라져 즉시 실패했다. → "왜 되는지" 설명 못 하는 성공은 검증이 아니다.

- **회색 버튼은 영구 실패가 아니라 '아직' 이다.** 비활성 컨트롤을 만나면 보통 "건너뜀" 이
  맞지만(다른 옵션이 꺼져 비활성인 경우), **곧 살아날 버튼**은 예외다. 재시도 루프가 있어도
  `Disabled` 예외만 그 루프를 빠져나가면 무의미하다.

- **정지·차단된 계정 걸러내기는 프로그램의 작업내역 CSV 가 답을 준다.** 로그인이 안 되면
  카페 작업까지 못 가서 나머지 열이 전부 `-` 로 남는다. 이 지문으로 계정을 제외한다.
  단 **계정별 마지막 결과**로 판정해야 한다 — 전체 기록에서 한 번이라도 실패한 계정을
  잡으면 지금은 되는 계정까지 버린다.

- **판정 로직은 반드시 한 곳에.** 세 프로그램 × 두 실행 경로(체인·세트)가 같은 판정을
  각자 갖고 있으면 한 곳만 고친 수정이 빈 구멍을 남긴다. 실측: 완료 줄 오인을 세트에서만
  고쳐 체인·가입에 그대로 남았고, 완료 지문이 **세 곳에 서로 다른 내용**으로,
  확인 시간 상수는 30초/45초로 갈라져 있었다. → `marks.py` 같은 단일 모듈로 수렴시키고
  **재정의를 정적 감사로 금지**한다. cf. [[단일-진실-원천]]

- **정적 감사(audit)가 실제로 버그를 잡는다.** 겪은 버그마다 항목을 추가하는 방식.
  실측으로 잡아낸 것: 옛 클릭 방식 잔존, 통합 창이 계정 파일을 직접 읽는 코드,
  세트 프로파일 경로 누락, 완료 판정 중복 정의. **눈으로 훑으면 한 곳을 놓친다.**

- **사람이 쓰는 도구를 실행 중에 고치면 진단이 뒤엉킨다.** 옛 인스턴스가 계속 돌아
  이미 고친 버그를 다시 겪는다. → 창 제목에 코드 시각을 박고, 코드를 고치면 자동 재시작.

- [[다경로-데이터-모순-디버깅]] — 체인 경로와 세트 경로가 같은 개념을 다르게 판정한 사례.
- [[부정판정-지문-오탐-방지]] — `캡차` 같은 범용 토큰을 로그인 실패 지문으로 쓰면
  정상 로그(캡챠 해독 서비스 설정)를 물어 되는 계정을 죽인다. **정상 확인을 먼저.**
- [[봇탐지-회피-순간밀도]] — 같은 계정이 같은 글에 연달아 댓글을 달 때 그대로 적용된다.
  간격 0이 문제이고, 명시적 차단 없이 **조용히 안 되는** 소프트 스로틀을 빈 결과로 감지.
- [[측정-지표-함정]] — 댓글 0개로 끝난 회차를 `완료` 로 세면 실패가 성공으로 보고된다.
- [[라이브-검증-프로토콜]] — 가짜 창(합성) 테스트 통과는 "로직 검증" 이지 실전 검증이 아니다.
  검증된 것과 미검증을 나눠 보고할 의무는 여기서도 같다.
- [[karpathy-guidelines]] — 판정 수렴은 surgical change 와 짝(고칠 지점이 하나가 된다).
- [[파이프라인-스킬-패키지]] — 이 컨트롤러는 단발 스크립트가 아니라 반복 실행 자산이라
  같은 폴더 해부도(계획·상세·독립 CLI·게이트)를 따른다.

## 내 생각 / 미해결 질문

- **자동 게이트로 바꿀 수 있는 규범이 어디까지인가.** "버튼 상태로 판단" 은 정적 감사로
  존재 여부만 검사할 수 있고, 실제로 그 순서를 지켰는지는 잡기 어렵다. 가짜 창(FakeApp)
  단위 테스트가 이 틈을 메운다 — 상태 대본을 주고 순서를 검증하는 방식.
- 같은 계정이 같은 글에 연속으로 댓글을 달 수 있는지는 **아직 실측 안 됐다.**
  0건이 나오면 도배 방지로 보고 글을 분산하는 쪽으로 간다.
- 벤더 패치로 로그 문구가 바뀌는 것을 어떻게 조기에 아는가 — 창 제목의 빌드 날짜 감지 +
  스모크 테스트가 현재 설계. 문구 변경은 "조용히 오작동" 이 아니라 즉시 중단으로 만들어야 한다.
