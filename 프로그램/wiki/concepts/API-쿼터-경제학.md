# API 쿼터 경제학

## 한 줄 정의

쿼터 있는 API 는 호출 하나하나가 **소모성 자산**이다 — 받은 응답은 무조건 디스크에 남기고,
파이프라인은 "어디서 끊겨도 이어받는" 모양으로 설계하며, 쿼터 규모가 바뀌면 설계도 다시 본다.

## 핵심 주장 / 속성

- **응답 = 자산, 즉시 캐시.** 비싼 응답을 메모리에만 들고 있다가 이후 단계(엑셀 저장 등)가 죽으면
  쿼터만 태우고 아무것도 안 남는다. 실사례: 트렌드 7,889개를 조회하고 캐시를 안 만들어 판정 버그
  수정 후 **전량 재조회**해야 했다. 캐시를 만든 뒤로는 판정 기준을 몇 번을 바꿔도 재실행이 공짜였다
  (같은 날 3개 카테고리에서 기준 변경·버그 수정·필터 추가로 총 5회 재판정 — 추가 콜 0).
- **캐시는 진행 중에도 주기 저장.** 배치 50개마다 flush + 종료 시 flush. 중간에 죽어도 그 시점까지는 자산.
- **소진 시나리오를 코드에 내장**: ① 429 → 다음 키 로테이션 후 같은 배치 재시도 ② 전 키 소진 →
  캐시 저장하고 **정상 종료**(예외 아님) ③ 재실행하면 캐시에 없는 것만 이어서 조회. "내일 다시 돌리면
  이어받는다" 가 보장되면 쿼터 소진이 사고가 아니라 일정 문제가 된다.
- **키 로테이션의 함정**: 프로세스 로컬 카운터로 로테이션하면(950콜마다) **새 프로세스가 이미 소진된
  키부터 다시 시작**한다. 서버 쿼터는 서버가 안다 — 로컬 카운터가 아니라 **429 응답을 로테이션
  신호**로 삼아야 잔여 쿼터가 있는 키를 놓치지 않는다 (실사례: 2번 키에 371콜이 남아있는데 1번 키
  429 만 보고 "오늘 끝" 으로 오판할 뻔).
- **쿼터가 설계를 결정한다** — 제약이 바뀌면 설계를 다시 본다:
  - 일 1,000콜 시절: 후보를 검색수 하한으로 압축(300→1,000), 대역을 나눠 여러 날에 걸쳐 조회.
  - 월 30,000콜(일일 무제한) 전환 후: 같은 작업을 하루에 전량. 압축 로직은 노이즈 필터로 용도 변경.
- **1콜의 밀도를 높인다**: 데이터랩은 1콜=키워드 5개 — 배치를 꽉 채우고, 상대비율 정밀도를 위해
  검색수가 비슷한 것끼리 묶는다. 무료 소스(ItemScout)로 대체 가능한 호출(keywordstool)은 아예 없앤다.
- **"기본 무료" vs "한시적 무료" 구분**: 한시적 구간은 언제든 유료화된다. 콘솔 한도를 기본 무료
  상한으로 잠가 과금 사고를 구조적으로 차단 ([[NAVER-API-HUB]] 월 30,000 잠금).

## 내 생각 / 미해결 질문

- 캐시 무효화 기준이 아직 없다 — 트렌드는 월이 바뀌면 낡는다. 캐시 파일명에 조회기간을 넣어
  (`trend_{cache}_{start}_{end월}.json`) 월이 바뀌면 자연히 새 파일이 되게 해뒀지만, 옛 파일 정리는 수동.
- 쿼터 사용량을 로컬에서 추적할 가치가 있나? 서버(콘솔)가 진실이라면 로컬 추적은 근사치일 뿐 —
  429 를 신호로 쓰는 현 방식이 더 단순하고 정직하다.
