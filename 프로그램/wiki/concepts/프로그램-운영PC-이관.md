# 프로그램-운영PC-이관

## 한 줄 정의

**돌고 있는 프로그램을 다른 PC 로 옮기는 일은 코드를 옮기는 일이 아니라, 저장소에 안 들어가는 것들을 옮기는 일이다.**

## git pull 로 가는 것과 안 가는 것

| | 어떻게 옮기나 | 빠뜨리면 |
|---|---|---|
| 코드·문서·도구 | `git pull` | — |
| **DB** | **백업 API 사본**(`conn.backup`), 파일 복사 아님 | 기록 전부 소실 → 전체 재스캔, 진행 중인 것 소실 |
| `.env` | 본보기 파일(비밀값은 비워서) | 경로가 엉뚱한 곳을 가리킨다 |
| **키 파일** | **사람이 직접** | — |
| 로그 | 안 옮긴다(빈 폴더만) | — |
| `.venv` | 그 PC 에서 새로 만든다 | 파이썬·의존성 충돌 |

**꾸러미로 만든다** — 위 중 "저장소에 안 가는 것"만 한 폴더에 모으고, 받는 쪽이 읽을 안내문(`읽어주세요.md`)과
인수인계(`운영PC-클로드에게.md`)를 같이 넣는다. 폴더만 넘겨도 따라올 수 있어야 한다.

## 옮길 때의 규칙 다섯

1. **DB 는 "안전 위치"로 만들어 넘긴다.** 자동 처리·자동 발송을 **끈 상태**로 저장한다.
   받는 쪽이 키를 넣는 순간 뭔가 나가면 안 된다. (그냥 복사하면 보내던 설정 그대로 켜진 채 뜬다.)
2. **DB 는 백업 API 로 뜬다.** WAL 모드에서 `.sqlite` 만 복사하면 최근 변경이 통째로 빠진다 —
   2026-09-22 실측으로 본체 2.4MB 에 WAL 4.4MB(우리), 206KB 미반영(형제 도구). 파일 복사를 해야 한다면
   **프로그램을 끄고 `.sqlite`·`-wal`·`-shm` 세 개 전부.**
3. **켜는 순서를 정한다.** 서로 창구를 부르는 프로그램이 있으면 **불리는 쪽이 먼저** 뜬다
   (댓글 관리 8005 → 부스터 8004: 부스터 첫 회차가 우리 창구를 부른다).
4. **겹치는 구간을 만들지 않는다.** 옛 PC 와 새 PC 가 같은 계정·토큰을 쓰면 호출 한도를 나눠 쓰고,
   자동이 양쪽에서 돌면 같은 일을 두 번 한다. 순서: **새 PC 올려 확인 → 옛 PC 자동 끄기 → 새 PC 자동 켜기.**
   ("옛 PC 자동 끄기"가 "새 PC 자동 켜기"보다 **먼저**다.)
5. **되돌리기는 DB 를 가져오는 조건이 붙는다** → [[중복방지의-DB-경계]]. "폴더를 그대로 두면 언제든 되돌린다"는 절반만 맞다.

## 하루 겪어 보니 — 실제로 걸린 함정들

- **`skip-worktree` 파일은 저장소를 안 따라간다.** 포탈 `start.bat` 이 그랬다. 개발 PC 에서 고쳐도 운영 PC 에는 안 간다 →
  그 PC 에서 손으로 고쳐야 한다. 옮기기 전에 `git ls-files -v` 로 `S` 표시를 훑는다.
- **경로가 PC 마다 다르다.** 폴더 이름까지 다르다(`snskit-booster` ↔ `메타댓글 부스터`). 기본값을 이름 하나에 매달지 말고
  후보를 여러 개 두거나 `.env` 로 덮는다. **못 찾으면 조용히 넘어가지 말고 경보.**
  > **이름이 달라서 드러난 게 다행인 경우도 있다.** 형제 도구의 `프리셋검증.py` 에 개발 PC 경로가 박혀 있었는데,
  > 폴더 이름이 달라 운영 PC 에서 **죽어서** 드러났다. 이름이 같았으면 **조용히 개발 PC 의 DB 를 읽고
  > "정의대로 나갔다"고 찍었을 것이다** — 그게 더 나쁘다. 박힌 경로는 죽는 편이 낫다.
- **동기화 폴더 경고는 사실 확인부터.** 바탕화면이면 무조건 OneDrive 라고 보면 오탐이 난다 —
  실제 `%OneDrive%` 밑인지로 판정한다. (동기화되는 자리면 SQLite 가 잠겨 기록이 멈춘다는 위험 자체는 진짜다.)
- **기동 구조가 바뀌어 있을 수 있다.** 운영 PC 포탈은 `start.bat` 이 아니라 `services.json` + 감시 프로세스였다.
  기동 순서도 배열 순서가 아니라 `order` 값이었다. 점검 코드가 옛 구조만 알면 **멀쩡한 것을 ❌ 로 잡는다.**
- **점검 도구가 대상보다 늙는다.** 형제 도구도 같은 일을 겪었다(옛 동작을 기대하는 판정 기준이 남아 결함이 아닌 것을
  계속 '재현됨'으로 보고). **오래 ❌ 인 항목은 고치기 전에 판정 기준이 아직 맞는지 먼저 본다.**
- **암호 게이트 같은 "붙어 오는 기능"** — 병합하면 포탈 전체에 로그인이 생기고, 설정 파일이 없으면 **아예 안 뜬다**
  (`gate_config.json` 을 모듈 최상단에서 읽는다). 병합 전에 "이 브랜치에 뭐가 같이 들어 있나"를 본다.

## 자체 점검 도구를 하나 둔다

형제 프로그램과 **같은 자리·같은 이름**(`tools\이관준비.py`)으로 두면 사람이 두 프로그램을 같은 손버릇으로 쓴다.
읽기만 하고, 비밀값은 찍지 않는다. 우리 20여 항목의 뼈대:

- **안전 위치** — 자동 처리·자동 발송 꺼짐, 발송 상한·시간대, 처리 시작 시각, 확인 주기
- **저장소 자리** — DB·백업 폴더가 동기화 밖인가, 하루 안쪽 백업이 있나, WAL 크기(복사 경고용)
- **키·모델** — 키 파일 형식(값은 안 찍는다), AI 키·모델, 발송에 필요한 값(번호·안내 이미지·링크)
- **남은 일거리** — 보내기 대기 0, 확인 필요 0, 24시간 오류 0
- **코드 상태** — 커밋 안 된 변경 없음 + HEAD
- **형제와의 공존** — 포탈 기동 순서, 형제 폴더를 찾는가

## 내 생각 / 미해결 질문

- 꾸러미를 **사람이 손으로 만든다**는 게 약점이다. "저장소에 안 가는 것" 목록은 프로그램이 알고 있으니
  `tools\이관꾸러미.py` 처럼 한 번에 만드는 것이 맞다(형제 도구는 `DB내보내기.py` 로 절반 했다).
- 점검 20항목 중 셋이 **환경 판정**(동기화·기동 구조·폴더 이름)이었고, 셋 다 처음엔 틀렸다.
  환경을 글자로 추측하지 말고 **그 PC 에서 실제로 물어보는** 방식이 맞다.
