# LLM 의미분류 필터링

## 한 줄 정의

"이게 팔 만한 제품/구매니즈인가" 처럼 **의미 판단이 필요한 분류는 숫자 신호로 못 가른다 — LLM 으로 분류하고,
프롬프트(규칙)·블록리스트(개별 제거)·허용리스트(개별 강제유지) 3층으로 운영**한다.

## 핵심 주장 / 속성

- **숫자 신호의 배신** — 쇼핑 키워드에서 "제품 vs 정보성"을 경쟁강도(상품수/검색수)나 쇼핑성 점수로 거르려 했으나 실패.
  사례 (2026-06-03): 신제품 브랜드 `비렌느스팟엑스`(검색11만, 경쟁강도 0.0) 와 노이즈 `변우석`(검색111만, 0.01) 이
  숫자로 구별 불가. 쇼핑성 점수도 `챗지피티`=0.96(높음·노이즈) / `어버이날선물`=0.08(낮음·제품) 로 거꾸로. → **의미만이 가른다.**

- **3층 운영 패턴** — ① **프롬프트 = 카테고리 규칙**(연예인·게임·주식 제거; 브랜드·니즈 유지 — 일반화) ② **blocklist = 개별 무조건 제거**
  ③ **allowlist = 개별 무조건 유지**(최우선). 블록/허용은 **LLM 캐시와 분리된 오버레이** → 사용자가 누락 키워드를 보내면
  리스트에 추가 후 **재분류 없이 출력만 재생성**(즉시·무료). 새 *카테고리* 규칙만 프롬프트에 넣고 재분류.

- **과제거 < 노이즈 잔존** — keep 가치가 높은 도메인(제품 발굴)에선 recall 우선. 원칙: **"애매하면 유지, 진짜 필요 없는 것만 제거."**
  좋은 키워드 하나 잃는 비용 > 노이즈 몇 개 남는 비용. 사용자 철학: "팔 수 있거나 힌트(액세서리·니즈)를 얻을 수 있으면 살려."

- **작은 샘플 테스트의 함정** — 20~120개 큐레이션 샘플에선 세 모델 다 만점이었으나, **전량(수천 개) 돌리니** gpt-5.5 가
  `샴푸·선크림`(제품), `어깨통증·유축기대여`(니즈) 를 과제거하는 약점이 드러남. **전량 돌려 제거목록을 사람이 검토**해야 진짜 오류가 보인다.

- **재판매 LLM 프록시의 함정** — ① 동시성 한도가 **계정(user)당** (`429 Concurrency limit exceeded for user`) → 키 2개 써도
  같은 계정이면 무의미, **병렬 < 순차**. ② 응답 레이턴시가 시점마다 출렁(51초~타임아웃) — 한가/혼잡 시간대 차이. ③ Codex(gpt-5.5)는
  싸지만 느리고 과제거 경향, Claude(opus)는 정확하나 비쌈.

- **캐시 파일명 충돌** — 두 프로세스가 같은 캐시 파일에 쓰면 진행분이 **뒤로 감**(작은 in-memory 상태가 큰 걸 덮어씀).
  입력 파일이 달라도 stem 이 같으면(`X_필터본` vs `X_전체키워드` 둘 다 `X.json`) 충돌. **한 작업 = 한 캐시 = 한 프로세스.**
  + 백그라운드 프로세스가 taskkill 로 안 죽는 경우 있음 → 순차 드라이버 하나로 통제.

## 내 생각 / 미해결 질문

- 의미분류는 결국 **사용자별 비즈니스 정의**에 종속(이 셀러는 빵·타이어 못 팖 → blocklist). 완전 자동화보다 **사람 검토 루프 + 리스트 누적**이 현실적.
- 모델 선택: 정확도 필요하면 opus, 비용/속도면 gpt-5.5 + 강한 프롬프트 + 리스트 보정. 작은 샘플로 고르지 말 것.
