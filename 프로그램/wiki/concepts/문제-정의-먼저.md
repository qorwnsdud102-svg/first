# 문제 정의 먼저 — 기능 이름은 마지막에

## 한 줄 정의

"○○ 기능이 필요하다"로 시작하지 않는다. **누가, 어떤 상황에서, 무엇 때문에 막히는지**를 먼저 한 문장으로 쓰고, 해결책은 여러 개 놓고 고른다. 화면이 직관적이지 않은 건 그리기 전에 "무엇을 끝내러 온 사람인가"를 안 정했기 때문인 경우가 많다.

## 3단계 (와니 E·F·G, 3등급 — 업계 표준 기법의 요약)

### 1) 문제 정의문
- 형식: **"[사용자]는 [상황]에서 [원인] 때문에 [어려움]을 겪는다."**
- 기능 이름을 넣지 않는다. 사용자가 **멈칫하는 순간**만 쓴다.
- ✗ "쇼핑앱에 찜 기능이 필요하다" — 이미 해결책. 답이 찜 버튼 하나로 좁아진다.
- ✓ "구매를 고민하는 사용자는 여러 상품을 비교하는 중에, 본 상품을 다시 찾는 길이 없어서 처음부터 다시 검색한다." → 찜·최근 본 상품·상품 비교를 나란히 놓고 고를 수 있다.

### 2) HMW (How Might We)
- 문제를 질문으로 바꾼다: **"어떻게 하면 [사용자]가 [상황]에서 [원하는 변화]를 이룰 수 있을까?"**
- 점검 3가지: ① 기능 이름이 들어갔나(들어가면 X) ② 해결책이 여러 개 나올 수 있나 ③ 아래 JTBD의 목적과 이어지나.

### 3) JTBD (Jobs To Be Done)
- 형식: **"[상황]에서 [무엇]을 해서 [원하는 결과]를 얻고 싶다."**
- 행동이 아니라 **원하는 결과**까지 쓴다. "음식을 주문한다"는 행동, "퇴근해서 집에 도착하자마자 먹고 싶다"가 결과 → 흐름에 도착 예정 시간 확인·시간 맞춰 주문·배달 현황이 추가된다.
- 흐름을 다 그린 뒤: **"이 흐름이 원하는 결과까지 이어지는가?"**

### 마무리 점검
기능을 정한 뒤 다시 문제 정의문으로 돌아가 **"이 기능이 그 어려움을 줄이나?"** — 아니면 우선순위에서 뺀다.

## 우리 도구에 쓰는 법 (예시)

- ✗ "대시보드에 시간대별 차트 탭 추가해줘"
- 문제 정의문: "대표는 아침에 광고를 볼 때, 어느 시간대에 예산이 새는지 숫자 표에서 찾아야 해서, 판단을 미루고 어제 설정을 그대로 둔다."
- HMW: "어떻게 하면 대표가 아침 5분 안에 어제 새던 시간대를 알아차리고 조치할 수 있을까?"
- JTBD: "아침 광고 점검 시간에 → 새는 시간대를 찾아서 → 예산을 옮기고 출근하고 싶다." → 차트보다 "어제 효율 최저 시간대 1줄 + [그 시간 예산 낮추기] 버튼"이 답일 수 있다.

Claude는 대표의 요청이 기능 이름으로 들어오면(“~탭 추가”, “~버튼 만들어”) **만들기 전에 위 문제 정의문을 한 줄로 되묻거나 스스로 적어 확인**한다. [[UI-UX-원칙]] §1의 1번 질문이 이것이다.
