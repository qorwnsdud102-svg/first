# 재고-품절-예측

## 한 줄 정의

재고가 여러 창고에 나뉘어 있을 때 창고마다 **「지금 몇 개 남았나」를 가장 믿을 수 있는 곳에서 구하고**, 최근 하루 판매로 나눠 **품절 예상일**을 낸다. 품절 전에 예약주문 안내를 걸어 「오늘 주문했는데 왜 2주 걸려요」 항의를 막는 게 목적이다.

## 원칙

- **API가 되면 API, 안 되면 사람이 센 개수에서 판매로 뺀다.** 창고마다 숫자 출처가 다를 수 있다(풀필먼트 API vs 사람이 센 개수 + 센 시각).
- **남은 재고 = 센 개수 − 그때 아직 안 나간 주문 − 센 뒤 주문.** 센 개수에는 결제됐지만 창고를 안 떠난 물건이 들어 있다. 「안 나감」은 주문마다 **채널의 배송 상태**로 가르고, 상태가 바뀐 것을 처음 본 시각을 따로 적어 두면 사람이 숫자를 매번 고칠 필요가 없다.
- **시각 규칙보다 상태 데이터.** 「16시 뒤 결제분」 같은 어림은 경계 근처 주문을 틀리게 세고 연휴마다 예외를 만든다. 사람이 운영하는 물류는 정해진 시각에 움직이지 않는다 — 송장·배송 상태가 있으면 그걸 쓴다.
- 개수는 **세트 × 주문 수량**으로 센다. 취소는 빼지 않고(안 나갔다), 반품은 뺀 채로 둔다(검수 전엔 다시 팔 수 있는지 모른다).
- **화면 한 줄 = 사람이 생각하는 단위.** API 단위(등록상품·옵션)를 그대로 보이면 재고 0인 중복 등록이 「품절」처럼 뜬다 — 같은 세트는 합친다.
- **입력 단위도 사람이 말하는 단위로**(낱개). 단위를 바꿀 때는 이미 적힌 자료를 먼저 보고, 옛 줄은 읽는 쪽에서 환산해 흡수한다.
- **어디에도 안 잡히는 재고**(회송·검수 대기)는 개수 + 사유만 적는 손 입력 칸으로. 다시 입고하면 지운다(안 지우면 두 번 센다).
- **자동으로 판단할 근거가 데이터에 없으면(검수 결과) 자동화하지 말고 사람이 적는 칸을 둔다.**

## 채널 상태 코드 — 「아직 안 나감」 판별

- 자사몰(카페24): `N00` 입금전 · `N10` 상품준비중 · `N22` 배송보류 → 아직 안 나감. `N20` 배송준비중부터 나간 것으로 본다.
- 네이버: `PAYED` 결제완료 → 아직 안 나감.
- 쿠팡 윙: `ACCEPT` · `INSTRUCT` → 아직 안 나감.
- 쿠팡 재고 API의 `vendorItemId` = 로켓 주문의 옵션 번호 — 주문 기록에서 옵션 → 제품·세트를 그대로 찾는다.

## 판정 규칙

- 품절 예상일 = 오늘 + ⌊남은 개수 ÷ 하루 판매⌋. 너무 먼 날짜(180일 초과)는 「6개월 넘게」로 — 2029년 같은 날짜는 뜻이 없다.
- 색 기준은 **생산 리드타임**에서 나온다: 생산 2주면 **14일 안 빨강**(예약주문을 걸 때), 21일 안 노랑. 상자 색은 가장 급한 줄을 따른다.
- **경고는 비관적인 쪽이 안전하다.** 판매 속도가 의도적으로 바뀐 이유(광고비 감액·연휴)를 알면 평균 기간을 바꾸기보다 그 이유가 끝날 때를 생각한다(7일 평균 유지).
