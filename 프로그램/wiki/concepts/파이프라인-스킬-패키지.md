# 파이프라인 스킬 패키지

## 한 줄 정의

여러 단계로 이어지는 자동화 작업 하나를 **SKILL.md(계획) · references/(상세) · scripts/(실행) · hooks/(자동화)** 네 종류 파일로 쪼개 **한 폴더**에 담은, 사람도 Claude도 돌릴 수 있는 재사용 스킬의 표준 해부도. [[클로드-베이커리-비유|4축]]을 추상이 아니라 **실제 폴더 레이아웃**으로 떨어뜨린 레퍼런스 구현.

## 왜 중요한가

[[바이브-코딩]]에서 "AI에 시키기"만 하면 결과가 매번 들쭉날쭉하다. 같은 작업을 **자산(반복 실행 가능한 스킬)**으로 굳히려면 파일을 어디에 어떻게 둘지 물리적 규약이 필요하다. competitor-finder([[competitor-finder]])가 그 규약을 한 폴더로 보여준 표본이라, 다음 도구를 만들 때 이 해부도를 복사하면 된다.

## 표준 해부도 (폴더 레이아웃)

```
<스킬-폴더>/
├── SKILL.md            # 계획: Phase A(입력)→B(STEP 실행)→C(보고) + 절대 규칙
├── CLAUDE.md           # 프로젝트 컨텍스트 (폴더 구조·실행 순서·주의사항)
├── README.md / 사용법.txt   # 사람용 사용법 (설치·CLI·트러블슈팅)
├── requirements.txt
├── api_keys.txt.example     # 비밀값은 .example 템플릿만 커밋, 실값은 gitignore
├── references/         # 상세 지식 — SKILL.md가 가리키는 곳 (progressive disclosure)
│   ├── api-guide.md        # 인증·엔드포인트·응답 필드
│   ├── surge-criteria.md   # 판정 기준·임계값·파라미터
│   └── ...
├── hooks/              # 자동화 게이트 (Hook)
│   ├── pre-*.sh            # 실행 전 환경 점검
│   ├── run-pipeline.sh     # 전체 일괄 오케스트레이션
│   └── post-*.sh           # 실행 후 정리·안내
└── scripts/            # 실행 단위 — 각 STEP = 독립 CLI
    ├── config.py           # 키 로드 + 인증 헤더 (공통 모듈)
    ├── step1_*.py          # 각각 python xxx.py --args 로도 단독 실행
    └── ...
```

## 전이 가능한 노하우 (다음 도구에 그대로 적용)

### 1. SKILL.md는 **코드가 아니라 실행 규칙(계획)**
Phase A(입력 확인) → B(STEP 순차) → C(완료 보고) + 맨 위 "절대 규칙" 5개. "무엇을 언제"만 적고 "어떻게"의 디테일은 코드/references로 위임. → SKILL.md가 가벼워야 [[스킬-스코프|description 매칭]]으로 떠올랐을 때 컨텍스트를 덜 먹는다.

### 2. references/로 상세를 분리 = **progressive disclosure**
인증 공식·판정 임계값·CID 목록 같은 무거운 지식은 SKILL.md 본문이 아니라 `references/*.md`에. SKILL.md는 "급등 기준은 `references/surge-criteria.md` 참조" 한 줄로 가리킨다. 필요할 때만 읽으니 토큰 절약 + 지식 갱신 시 한 파일만 고침.

### 3. **이중 구동** — 사람 CLI ↔ Claude 오케스트레이션
각 STEP가 `python scan_surge.py --title 탈모 --cats ...` 로 **단독 실행**되면서, 동시에 SKILL.md를 통해 Claude가 순서대로 돌릴 수도 있다. 한 경로(예: 메타 로그인 모달로 크롤링 막힘)가 막혀도 사람이 다른 STEP만 손으로 재실행 가능. 자동화가 깨져도 수동 폴백이 산다.

### 4. **파일 핸드오프**로 단계 간 느슨한 결합
STEP1 → `신규브랜드_TOP30.xlsx`/`급등키워드.json` → STEP2의 입력. 단계끼리 공유 메모리·전역 상태 없이 **파일로만** 손을 잡는다. → 중간부터 재실행 가능, 한 STEP 실패가 전 단계 산출물을 날리지 않음. (vault [[index]] "프로그램 격벽 원칙"의 단계 버전 — 통신은 파일/HTTP로만.)

### 5. **우아한 실패(graceful degradation)** 를 설계에 박는다
- SKILL.md 절대 규칙: "STEP 실패 시 3회 재시도 → **부분 결과라도 보고서 생성**".
- `run-pipeline.sh`: 신규 브랜드 엑셀이 안 만들어지면 메타 크롤링을 건너뛰고 계속 (`set -e` 와 공존하는 명시적 분기).
- `SKIP_META=1` 토글로 키워드 분석만 따로. → 현실의 크롤링/외부 API는 깨지는 게 기본값이라, 0건이어도 끝까지 가도록.

### 6. **정책은 데이터, 메커니즘은 코드**
대형 브랜드 제외 `EXCLUDE_BRANDS`, 제품 접미사 `SUFFIXES`, 일반명사 `GENERIC_KEYWORDS` 리스트 + 급등 임계값(상대비율 15→40, 검색량 0→300). 도메인 지식을 **리스트/상수**로 빼두고, "다른 카테고리 적용 시 수정 포인트"가 어디를 고칠지 문서로 명시. → 카테고리 바꿔도 코드 본문은 안 건드리고 리스트만 교체해 재사용.

### 7. **훅이 파이프라인을 감싼다** ([[Hook]]의 구체 사례)
- `pre-scan.sh` = 실행 전 게이트: python/패키지/playwright/API키 존재 + `YOUR_` 예시값 잔존까지 검사하고 실패 시 `exit 1`.
- `run-pipeline.sh` = 오케스트레이션 (`set -e`, STEP 1→4 순차, 사이사이 안내 출력).
- `post-analyze.sh` = 끝나고 산출물 정리·경로 안내.
→ AI가 본 작업을 시작하기 *전에* 환경 실수를 자동 차단하는 위생 게이트.

### 8. **환경 가정을 코드+문서 양쪽에 명시**
`PYTHONIOENCODING=utf-8`(Windows 한글 깨짐), 서버 시간차 자동 보정(`config.calc_time_diff`), api_keys.txt 탐색 경로 fallback(루트→scripts/). 현실 함정을 트러블슈팅 섹션과 코드 양쪽에 박아 "내 PC에선 됐는데"를 줄임. ([[karpathy-guidelines]] Think Before Coding — 가정 명시.)

## 외부 검증 — [[마케팅/근육돌이]] 파이프라인 규약 (2026-07~08 신규 11편)

이 페이지의 8개 노하우는 사장님 개인 도구(competitor-finder) 하나에서 추출한 것이라 **표본 1**이었다. 광고대행사 CCFM이 **영상 자동화 5단계·하루 소재 50~1,000개** 규모로 굴리며 정착시킨 규약이 여기 붙는다 — **독립 출처의 교차 검증**이자, 없던 규약 3개의 추가.

### 교차 검증 — 폴더 핸드오프 4단계 (§4 파일 핸드오프의 독립 확인)

> 1. **입력을 폴더나 시트 하나로 정한다** — 여기에 처리 대상이 쌓인다
> 2. **처리 단계를 나눈다** — 수집 · 정리 · 판정 · 출력
> 3. **각 단계는 앞 단계의 결과 폴더를 보고 미처리된 것만 처리한다**
> 4. **다 끝난 건 완료 폴더로 옮긴다** (71348:778-790)

**"중간에 하나가 실패해도 그 자리부터 다시 돌릴 수 있다. 처음부터 다시 안 해도 된다."** / **"각 단계가 서로를 몰라도 폴더 규칙만 맞으면 돌아간다."**

→ §4(파일 핸드오프)·§5(우아한 실패)가 **다른 조직에서 독립적으로 같은 형태로 정착**했다. 차이는 하나 — 근육돌이 쪽은 **완료 폴더로 이동**까지 규약에 넣어 "미처리 = 아직 입력 폴더에 있는 것"이 자연히 성립한다. competitor-finder는 산출물 파일명으로만 구분하므로, **완료 이동 규칙을 템플릿에 추가할 여지**가 있다.

### 신규 규약 ① 사람 게이트는 "비싼 작업 직전"에 둔다

> **"무한 자동화는 위험합니다. 잘못된 게 그대로 끝까지 가버리거든요.
> 그래서 저는 비싼 작업 바로 앞에 사람 확인 게이트를 둡니다. …여기서 5분 보면 뒤에서 몇 시간 아낍니다."** (71348:792-798)

- 예: **영상 생성처럼 비용이 크게 드는 단계 직전**에 앞 단계 결과를 사람이 한 번 보는 자리.
- 같은 원리의 다른 이름 — **"중간 검문소"**: 6단계짜리 조사를 시켰으면 **3단계쯤에서 한 번 결과를 본다.** 앞 단계가 틀렸는데 뒤를 계속 돌리면 그 뒤가 전부 쓰레기가 된다("틀린 리뷰를 뽑았는데 그걸로 키워드를 뽑고 그 키워드로 카피를 만들면 카피가 아무리 예뻐도 못 쓴다"). (71348:386-392)
- → 이 페이지 §7의 훅 3종(pre/run/post)은 **실행 전·후** 게이트만 갖고 있다. **파이프라인 *중간*의 사람 게이트**는 없던 축이다. 비용(토큰·API·시간)이 급증하는 STEP 직전에 `--pause` 또는 확인 파일 대기를 두는 패턴을 부트스트랩 템플릿에 추가 검토.

### 신규 규약 ② "예상 대 실제" 자체 검증을 산출물마다 박는다

실제 사고: 자막 자동 부착 지시문을 한 번 바꿨는데 **추출 로직이 깨져 일부 컷의 자막이 통째로 빠졌고, 아무도 못 잡고 그대로 나갔다.** 결국 영상을 눈으로 본 사람이 발견. (71348:996-1004)

> **"만들어야 할 컷이 12개면 결과 파일에 12개가 다 있는지 기계적으로 세어본다. 예상과 실제를 한 번 비교하는 것. 다르면 그 자리에서 잡는다.
> 이 '예상 대 실제' 비교 한 줄이 사고를 정말 많이 막아준다."**

- **검증 2단계**: ①**기계적 확인**(개수·형식·파일 유무처럼 숫자로 확인 가능한 것) ②**다른 시선의 검토**(만든 사람이 아닌 관점 — 사람이든 다른 AI든). **"만든 주체가 자기 걸 검토하면 잘 안 보인다. 사람이나 AI나 똑같다."** (71348:1040-1048)
- **확인 안 되는 건 안 된다고 명시**: 자막 개수·파일 유무는 기계가 확인하지만 **목소리 톤이 자연스러운지는 사람이 들어봐야 한다. 그걸 확인한 척하면 그게 사고로 이어진다.** (71348:1006)
- → 이 페이지 §5(우아한 실패)는 "부분 결과라도 보고서 생성"까지만 정한다. **부분 결과가 *얼마나* 부분인지를 기계가 세어 보고**하는 규약이 빠져 있었다. §미해결질문의 **"부분 결과라도 보고서의 정확성을 누가 검증하나"**에 대한 직접적인 답이기도 하다.

### 신규 규약 ③ 기준 파일은 재작성이 아니라 버전 증가

> **"같은 일을 두 번째 시킬 때는 지시문을 다시 쓰지 마세요. 첫 번째에 잘 나온 지시문을 파일로 저장해두고 그걸 재사용하세요. 매번 새로 쓰면 매번 다른 품질이 나옵니다."** (71348:394-398)

- **한 번에 한 변수만 바꾼다** — 결과가 마음에 안 든다고 지시문을 통째로 갈아엎으면, 다음에 좋아졌을 때 **뭐 때문에 좋아졌는지 모른다.** 역할만 바꿔보고, 그다음에 단계만 바꿔보는 식. (71348:1028-1032)
- **잘 나온 지시문 + 그때의 결과물을 함께 저장**하고 팀 단위로 공유. (71348:1034-1036)
- → 이 페이지 §6(정책은 데이터)은 **리스트·임계값**을 상수로 뺐다. 여기에 **그 상수 파일의 변경 이력**(버전 증가 + 한 번에 한 변수)을 규약으로 더한다. §미해결질문의 "판정 임계값(15→40, 0→300)의 근거는 있으나 회귀 테스트는 없음"과 맞물린다 — **버전 + 그때의 결과물 보관이 곧 회귀 기준선**.

### 보너스 — 자동화 전제 두 가지

- **"양을 늘리기 전에 한 사이클을 손으로 완주해보세요."** 손으로 한 번도 안 해본 일을 자동으로 100번 돌리면 뭐가 잘못됐는지 알 방법이 없다 — **100개의 쓰레기가 나올 뿐.** 한 번 손으로 해보면 어디가 아픈지 알고, 그 아픈 데를 알고 나서 자동화한다. (71348:808-814)
- **"기준을 숫자나 문장으로 못 적으면 자동화도 못 합니다. 자동화의 시작은 도구가 아니라 기준입니다."** (71608:516)

- [[Claude-Skill]] · [[스킬-스코프]] — 스킬이 "무엇이고 어디 살고 언제 깨어나는지". 본 페이지는 "그 스킬 폴더 *안을* 어떻게 채우는지".
- [[Hook]] — §7 pre/run/post 훅 3종이 그 개념의 실제 적용.
- [[karpathy-guidelines]] — §2 Simplicity(SKILL.md 가볍게)·§6 정책/메커니즘 분리·§8 가정 명시가 4원칙과 직결.
