# 봇 탐지 회피 = 총량 아닌 순간 밀도

## 한 줄 정의

크롤 총량이 낮아도 초 단위로 몰리는 톱니 패턴이 IP 단위 봇 판정을 유발한다 — 방어는 전역 호출 간격 + 지수 백오프 쿨다운.

## 핵심 주장 / 속성

- **사례 (2026-07-20)**: 네이버 검색페이지 IP 단위 일시 접근 제한 발생. 실측 평균은 **160 fetch/h(22초에 1건꼴)로 매우 낮았는데도** 차단됐다. 평균은 한가한데 배치가 돌 때만 초 단위로 몰리는 **톱니 패턴**이 원인. 유발 지점은 크롤 루프에 키워드 간 지연이 **아예 0초**였던 것. → **간격이 0이 아니게 된 것 자체가 핵심 변화**. 1초냐 2초냐는 부차적(네이버 실제 임계값은 관찰로만 판단, 확인 불가).
- **3중 방어**:
  1. **전역 페이스** — 프로세스 **전역** 락 + 랜덤 간격. 광고그룹 사이클이 동시에 여러 개 돌아도 IP 기준 총 호출률이 고정. (사이클별 지연은 무의미 — 겹치면 순간 밀도가 다시 올라감.)
  2. **동시 연결 제한 + 슬롯 초과 skip** — 동시 브라우저 N개, 슬롯 대기 초과 시 이번 사이클만 skip. 무한 대기로 스케줄러 스레드가 전부 묶여 **다른 작업(다른 데이터 경로)이 굶는 것** 방지.
  3. **차단 쿨다운** — 감지 시 전면 중단 + 지수 백오프(하드 30분→2배씩 상한 4h / 소프트 10분). 쿨다운 중엔 요청 자체를 안 함. cf. [[부정판정-지문-오탐-방지]] — 감지가 오탐이면 이 쿨다운이 정상 트래픽을 죽인다.
- **소프트 스로틀 신호** — 명시적 차단 페이지 없이 **특정 영역만 안 뿌리는** 방식으로도 제한을 건다(예: 광고 영역 누락). 명시적 차단만 보지 말고 **연속 빈 결과**를 감지 신호로 채택.
- **쿨다운 상태는 보통 in-memory** → 재시작하면 백오프가 리셋되어 1회 재탐침. 차단 지속 중이면 즉시 재감지(피해 1~2건)라 의도된 트레이드오프.
- **재발 시 대응 순서**: ① 간격(PACE) 상향 → ② 만기 분산(jitter, 대량 작업이 한꺼번에 만기돼 버스트로 몰리는 것 방지) → ③ 주기(interval) 상향. 지수 백오프가 1차 자동 방어를 맡음.

## 내 생각 / 미해결 질문

- 임계값을 알 수 없으므로 목표는 "안전 상수" 가 아니라 **자동 회복 구조**(전역 페이스 + 지수 백오프). 상수는 재발 시 되돌릴 1순위 값으로만 관리.
