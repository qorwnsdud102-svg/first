# snskit-booster — 개념 페이지 원문 이관

위키 `프로그램/wiki/concepts/` 정리(2026-10-06) 때 개념 페이지에서 빼낸 날짜별 실측·사건·결정 기록 원문. 원칙은 위키 페이지에 남아 있다.

## from [[주문-전달-실물-대조]]

### 왜 (2026-09-20 실측)

[[snskit-booster]] 첫 실주문 날, 패널이 말하는 진행 상황이 **양방향으로** 틀렸다.

| 패널이 말한 것 | 실제 |
|---|---|
| FB 여성 좋아요 `남음 4`(1개 처리) | 게시물 좋아요 **+4** 반영 |
| FB 여성 랜덤 댓글 "2개 처리" | 게시물 댓글 **0건** |
| FB 커스텀 댓글 `Pending`·시작 카운터 0 | 4~5시간째 정말로 0건 |
| 2026-08-03 주문 `Completed`·시작 카운터 공백 | 댓글은 실제로 달려 있었다 |

`start_count`·`remains` 는 작업자가 보고하는 값이라 지연·누락·과대보고가 섞인다. 이 숫자만 보고 "됐다/안 됐다"를 판정하면 **돈이 나간 뒤에도 몇 시간 동안 모른다**.

### ⚠️ 대조하는 쪽도 틀린다 (2026-09-22 — 이 페이지를 한 번 뒤집은 날)

위 규칙을 지키다가 **정반대로 틀렸다.** 메타 실측을 근거로 "FB 피드 게시물은 배달이 안 된다" 고 보고했는데,
대표가 브라우저로 열어 보니 **좋아요 225 · 댓글 34** 가 멀쩡히 있었다.

원인: `/me/accounts` 가 주는 페이지 id(`586083164589708`)와 그 게시물이 실제로 사는 페이지
id(`61574054860277`)가 다르다. `{586…}_{게시물id}` 로 물으면 **오류 없이 좋아요 0 · 댓글 0** 이 돌아온다.
릴스(`/reel/`)는 같은 방법으로 제대로 읽힌다 — 그래서 **"릴스만 배달된다" 는 착시**가 생겼다.

| | API 가 주는 값 | 실제(브라우저) |
|---|---|---|
| FB 피드 게시물(광고 전용) | 좋아요 0 · 댓글 0 | 좋아요 225 · 댓글 34 |
| FB 릴스 | 좋아요 222 · 댓글 33 | 같음 |
| IG 미디어 | like_count 정상 | 같음 |

**그래서 규칙이 하나 늘었다:**

6. **대조군으로 눈금을 먼저 맞춘다.** 실측 도구를 믿기 전에, **실제로 달린 게 확실한 대상**을 같은 방법으로 읽어
   숫자가 맞는지 본다. 한 종류(릴스)에서 통한 판독법이 다른 종류(피드)에서도 통한다는 보장은 없다.
7. **0 과 "못 읽음" 을 구분해 표시한다.** 도구가 0 을 줄 때 "안 달렸다" 가 아니라 **"내 도구가 못 읽는다"** 를
   먼저 의심한다([[모름-vs-0-표시-규약]] 과 같은 정신 — 이번엔 그 규약을 지킬 쪽이 우리였다).
   `배달확인.py` 는 FB 피드 줄에 `0 은 '미전달' 이 아니라 '모름'. 브라우저로 확인` 을 찍는다.

> 돈·중단 같은 결정을 **실측 하나로** 내리기 전에 사람에게 화면으로 교차 확인을 청한다.
> 이 건은 "15,300원이 버린 돈" 이라는 보고와 "snskit 에 환불 문의" 라는 제안까지 갔다가 되돌렸다.

### 수량은 늘 조금 모자란다 (2026-09-22 실측)

기준값을 박고 잰 밤샘 드립에서 **IG 커스텀 댓글은 세 게시물 전부 주문 11개 → 실측 +10** 이었다.
셋 다 똑같이 1개 모자라다. 원인은 모른다(중복 문구가 걸렸는지, 계정 하나가 실패했는지).

→ **판정 기준을 "주문 수량과 정확히 같은가" 로 잡으면 매번 실패로 읽힌다.** `수량 −1` 근처면 정상으로 닫고,
**0 증가**인 건만 따로 추적한다. 좋아요는 정확히 맞았다(10개 주문 → +10, 세 건 모두).

완료 표시까지 걸린 시간은 상품마다 다르다 — IG 커스텀 댓글은 어제 16건이 **60분~5시간**에 흩어졌다.
"몇 분 안에 안 붙었다" 로 고장 판정하면 안 된다.

### 2026-09-17 보강 — 실사용 전 감사·소크가 뚫은 곳

"네 겹"을 다 갖춰도 **상태 머신의 이음매**에서 돈이 샜다. 한 가지씩 넣는 단위 테스트로는 안 보였고, 감사 4갈래(백엔드 장애·동시성·돈 경로·운영자 UX) + 장애를 섞은 장기 소크(가상 7,800일, 강제 종료 348회)가 찾았다.

- **"접수 불명" 판정은 예외 종류로 가른다** — `ConnectionError` 를 통째로 "안 닿음"으로 보면 안 된다. 보낸 뒤 끊김(RemoteDisconnected·RST·TLS EOF·ChunkedEncoding)은 **접수됐을 수 있음**. "안 닿음"은 연결 거부·DNS 실패(`NewConnectionError`)·연결 타임아웃뿐. 실제 윈도 소켓으로 FIN/RST 를 재현해 확인.
- **이미 나간 항목 제외는 회차 상태와 무관하게 항상** — 재시도 때만 거르면, 강제 종료 뒤 사람이 안내대로 정리해도 앞 항목이 다시 나간다.
- **첫 접수 불명이 나오면 그 실행의 남은 발주를 멈춘다** — snskit 점검 중이면 한 사이클에 수십 건이 전부 불명이 되고 상한만 소진된다.
- **"실패로 정리" 버튼은 접수 불명에만** — 접수된(Pending) 주문을 사람이 "미접수"로 바꿀 수 있게 열면, 재시도가 같은 항목을 또 산다. 정리 경로를 넓힐 때 가장 쉽게 새는 곳.
- **꺼짐은 실행 단계에서 본다** — 게시물 "자동 끄기"를 계획 단계에서만 보면 이미 잡힌 2·3차가 나간다. 광고가 보관·삭제돼 조회 응답에서 **사라진** 것도 "마지막 값 ACTIVE"로 굳으니, 전체 동기화 성공 시 안 보인 행을 `NOT_RETURNED` 로 표시해 보류.
- **지출은 max(예상, 실제 청구)** — 캐시된 단가로만 합산하면 단가 인상 뒤 상한을 넘는다(소크: 최대 79% 초과). 청구가 예상보다 크면 경고 + 서비스 목록 강제 갱신, 캐시는 30분마다.
- **시뮬레이션 기록은 실전에 섞이지 않게** — 시뮬 지출이 같은 날 실주문 상한을 막고, 시뮬로 "완료"된 회차는 실전 전환 뒤 영영 안 나간다. 전환 전에 시뮬 기록을 지우거나 실지출 계산에서 뺀다.
- **일부 항목만 빠진 회차는 열린 주문이 없어진 뒤 빠진 것만 1회 재시도** — "전부 취소일 때만"이면 조용히 누락, "하나라도 실패면"이면 이미 끝난 회차를 다시 연다.
- **포기와 보류를 구분** — 일시 오류·서비스 목록 누락·프리셋에서 회차 정의가 사라진 경우는 재시도 횟수를 쓰지 않는 **보류**. 아니면 잠깐의 장애로 회차가 영구 포기된다.
- **운영 스크립트도 돈 경로** — 창 제목으로 `taskkill` 하는 stop.bat 은 같은 제목의 크롬 창까지 죽이고, 사이클 도중 강제 종료는 `Placing` 을 남긴다. 기동 시 `Placing` 이 보이면 자동모드를 끄고 알린다. 비상정지는 포탈 없이 `127.0.0.1` 로 바로 설정을 내리는 배치로.

### 2026-09-19 보강 — 사람 승인 경계 (운영 기능 묶음 통합 리뷰)

운영 편의 기능(승인 대기열·AI 댓글·프리셋 적용 범위·실주문 전환)을 7갈래로 동시에 붙이자, 이중 결제가 아니라 **"사람이 안 본 것이 돈이 되는"** 구멍이 이음매마다 났다. 통합 리뷰 3회가 실패 테스트로 증명한 것만 추렸다.

- **승인 실행은 채우지 않는다** — 승인 카드에서 사람이 댓글 줄을 비웠는데 엔진이 "아직 안 채움"으로 보고 풀·AI에서 새로 채워 주문했다. 이미 쓴 줄을 빼고 풀에서 다시 채우는 것도 같은 구멍. 승인·대기열 실행에서 빈 항목은 **건너뜀**, 채우기는 사람 없는 자동 회차에서만.
- **공유 자원에는 검토된 것만** — AI 문구를 생성 즉시 공용 댓글 풀에 저장하니, 승인 대기 중인 문구가 승인 없는 다른 게시물로 나갔다(거부해도 풀에 남음). 저장은 사람이 승인했거나 실제로 나간 줄만. 미리보기는 아무것도 쓰지 않는다.
- **모드가 바뀌면 그 전 모드의 결정은 무효** — 시뮬레이션 중 "승인 → 시간대 밖이라 대기열" 된 건이 실주문 전환 뒤 실제 주문이 됐다. 시뮬→실주문 전환(마법사·설정 어느 길이든)은 대기열 승인을 다시 승인 대기로, 승인 행엔 결정 당시 모드를 적어 두고 실주문 사이클은 시뮬 때 결정된 것을 실행하지 않는다.
- **"새 게시물부터"는 정의 전체를 박는다** — 프리셋 수정의 적용 범위를 항목만 얼렸더니 승인 필요 여부·시점이 진행 중 게시물로 새어, 승인 필요였던 회차가 승인 없이 나갔다. 주문되지 않은 회차 전부(승인 대기·건너뜀 포함)에 옛 회차 정의 스냅숏.
- **표시 금액도 엔진과 같은 규칙으로** — 예보가 시뮬 기록을 "이미 나감"으로 세서 실주문 전환 뒤 확인창이 ₩0 인데 실제 3건이 나갔다. 확인창 숫자를 만드는 함수는 엔진의 필터를 **같이 불러** 쓴다(복제 금지).
- **스키마에 늦게 더한 열은 버전을 올린다** — 같은 버전 단계 안에 열을 추가하면 이미 그 버전인 DB 는 영영 못 받아 사이클이 통째로 500. 배포 전 실데이터 복사본으로 이전 버전→새 버전 이행을 리허설.

**릴스 둘이 63.3%.** FB 만 보면 릴스가 피드의 **6.6배**다(소재별로는 1.8~12배).

| 구좌 | 링크 모양 | 대표/변형 | 656건 중 |
|---|---|---|---|
| FB 릴스 | `/reel/{id}` | **전부 변형** | 21 |
| FB 피드 | `/posts/{id}` | **전부 대표** | 315 |
| IG | `/p/{code}` | 대표 307 · 변형 13 | 320 |

2026-09-22 확정한 배분:

| 대상 | 프리셋 | 게시물당 |
|---|---|---|
| 대표(FB 피드 + IG 한 덩어리) | IG 는 기본 수량, **FB 는 경량** | 4,670원 |
| FB 릴스 변형 | 기본 | 6,240원 |
| IG 변형 | 기본 | 3,350원 |

대표 게시물은 FB·IG 가 한 주문 단위라 **FB 만 줄일 수 없다.** 그래서 "FB 는 경량, IG 는 기본" 을 섞은 프리셋을 따로 만들고,
한 플랫폼만 주문하는 변형에는 기본 프리셋을 준다(설정 `variant_preset_id`). 게시물당 4,920원이 절약된다.

FB 피드가 5.5% 라는 것과 **FB 피드에 주문이 안 붙는다**는 것은 다른 말이다.
2026-09-22 에 이 둘을 섞어 "피드는 돈만 나가고 아무것도 안 달린다" 고 잘못 보고했다 —
실제로는 달렸고, **메타 API 가 그 게시물을 못 읽었을 뿐**이다([[주문-전달-실물-대조]] §대조하는 쪽도 틀린다).
